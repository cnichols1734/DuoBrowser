# DuoBrowser production audit — October 27, 2026

## Scope and verdict

**Audit completed before implementation.** Baseline: `2569427` (runtime `4a5a434`), Xcode 27.1 / iOS 27.1. This is a capable full-width browsing prototype, not a launch-ready browser. No Safari parity, private-mode guarantee, credential interoperability, App Store eligibility, or hardware performance certification is established.

Evidence: source inspection; installed SDK headers; the existing 21 scroll, 12 archive, and 24 synthetic layout checks; the [eight-site native simulator report](SITE_QA_2026-10-27.md). Those previously passing tests are baseline evidence, not new tests of future changes. No credentials, purchases, authenticated feeds, or physical-device tests were performed. Status describes the baseline, and remains frozen here; subsequent work must be recorded separately.

Definitions: **Implemented** = application integration exists, with stated verification limits. **Partial** = only part of the required behavior exists. **Missing** = no application integration. **Unverified** = mostly platform-supplied capability whose real interoperability has not been established. “Missing” is not evidence of an exploit; these are release gaps.

## Priorities, dependencies and release gates

1. **P0 foundation: profiles and durable state.** Explicit persistent normal store; separate ephemeral private session; private tab grouping and clear lifecycle; no private archives/history/previews on disk; background cover. Add bounded validated versioned persistence, backup/recovery, write coalescing, lazy restored tabs and memory-pressure policy. This precedes every history/download/permission/site-preference feature. Acceptance: storage isolation with cookies/localStorage; normal restart; private teardown/restart; corrupted archives; tab switching and form preservation; no private disk artifacts in app-owned storage.
2. **P0 navigation and origin trust.** URL resolver and select-all address field; WKUIDelegate windows with provided configuration; exactly-once JS dialog completion; guarded external schemes, default certificate trust and clear failure UI. Depends on profiles so child windows cannot cross privacy stores. Acceptance: synthetic GET/POST target blank/opener/window.close, alert/confirm/prompt cancel/close/navigation, popup cap, invalid TLS, blocked executable schemes, host:port parsing, back/forward/fragment/SPA and form state.
3. **P0 transfer and permissions.** WKDownload response/action conversion, temporary destination and native Files export with cleanup/cancellation; WebKit upload picker retained; camera/mic/location purpose strings and origin-based prompts. Depends on phases 1–2. Acceptance: attachment/blob/download link, unsupported MIME, duplicate/unsafe names, cancel/error/private teardown, Files/Photos/capture selection/cancel, grant/deny/revoke. No login credentials required for synthetic tests.
4. **P0 geometry and accessibility.** Correct bottom `obscuredContentInsets`; site/profile preferences; reserved-region conversion and conservative camera fallback, no global width hacks; scalable control typography and native focus. Depends on lifecycle/navigation to reject stale work. Acceptance: closed/open/partial/rotation, zoom and keyboard, safe-area changes, fixed bottom buttons, nested/ambiguous layouts and rollback, VoiceOver/Reduce Motion/large text, bounded observer workload.
5. **P0 library and recovery; P1 minimal conveniences.** Local history/deletion and bookmarks in one library; native share/find; site mode in existing page menu; pull refresh; bounded previews and tab management. Recovery must not silently replay POST or serialize sensitive form state. Depends on profile/persistence and navigation. Acceptance: successful visits only, private exclusions, history delete survives restart, favorites duplicates, share/find cancellation, menu and focused-control accessibility.
6. **P0 credential and release verification; P1 media/performance.** Confirm correct Apple browser eligibility/signing before claiming arbitrary-site passkeys. Signed device matrix with Apple Passwords and a third-party provider; persistent real-site login/logout; permission hardware, PiP/DRM, thermal/battery/memory/scroll profiling. Re-run the eight supplied sites against the final code. No authenticated result without an authorized test account. Release remains blocked until these checks and earlier P0 gates pass.

No cloud AI is needed for these phases. If on-device classification is later useful, it may select a bounded, validated action from sanitized geometry. It must never generate executable page code, inspect credentials, or run in the scroll frame loop. Deterministic safe fallback remains mandatory.

## Design and engineering health

Provisional code-review rubric (0 absent, 1 major gaps, 2 partial, 3 solid with gaps, 4 verified): accessibility **2/4**, performance **2/4**, theming **3/4**, responsive behavior **2/4**, simplicity / native patterns **3/4** = **12/20**. This is not a WCAG or performance certification.

Positive foundations: stable live WKWebView, main-actor ownership, independent chrome progress, bounded reversible layout script in isolated content world, no native page-message bridge, no telemetry, no trust bypass, downsampled in-memory previews, native glass/semantic colors and meaningful fixture coverage. Preserve these.

Highest risk: privacy/session architecture and opener/request preservation (P0), permission/transfer integration and real credential eligibility (P0), camera/bottom-control collisions (P0), excessive retained web views and repeated archive encoding (P0 lifecycle/performance). Fixed typography and debug-only options shown in production are P1 polish. Avoid solving these with more permanent buttons: retain back/address/tabs; put contextual actions in the existing page menu, history/bookmarks in one library sheet, privacy in tab overview. Hide diagnostic toggles in release builds.

## Platform references

- [Apple: WKWebsiteDataStore](https://developer.apple.com/documentation/webkit/wkwebsitedatastore): default persistent versus nonpersistent storage.
- [Apple: Passkey use in web browsers](https://developer.apple.com/documentation/authenticationservices/passkey-use-in-web-browsers), [supporting passkeys](https://developer.apple.com/documentation/authenticationservices/supporting-passkeys), [default browser requirements](https://developer.apple.com/documentation/xcode/preparing-your-app-to-be-the-default-browser): distinguish browser eligibility from an embedded app web view. Approval and hardware interoperability remain external gates.
- [Apple: HTML Password AutoFill](https://developer.apple.com/documentation/security/enabling-password-autofill-on-an-html-input-element): system/website integration, not credential scraping.
- [Apple: file upload delegate](https://developer.apple.com/documentation/webkit/wkuidelegate/webview(_:runopenpanelwith:initiatedbyframe:completionhandler:)): iOS supplies uploads by default when not overridden.
- [Apple: media permission delegate](https://developer.apple.com/documentation/webkit/wkuidelegate/webview(_:requestmediacapturepermissionfor:initiatedbyframe:type:decisionhandler:)), [download destination](https://developer.apple.com/documentation/webkit/wkdownloaddelegate/download(_:decidedestinationusing:suggestedfilename:completionhandler:)).
- Installed iOS 27.1 SDK: `WKWebView.h` documents `interactionState` including form data and `obscuredContentInsets` (public since iOS 26) adjusting fixed/sticky edge content; `WKUIDelegate.h` exposes geolocation permission on iOS 27 and supplied-configuration window creation. SDK availability was checked locally rather than inferred from Safari behavior.
