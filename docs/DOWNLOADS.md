# Downloads

November 12, 2026. Native download management; no merge or release is implied.

Page options → Downloads opens a native list with filenames, byte progress, individual cancellation, retry where WebKit can safely repeat the transfer, Quick Look preview, Save to Files, and removal. Downloads finish without interrupting the page. A small download indicator on Page options remains visible while transfers are active or a new result is waiting in Downloads. Larger text uses a simpler row without the decorative file icon; controls have accessible labels and 44-point action targets.

Normal downloads belong to the browser session rather than the source tab. Closing that tab keeps an active transfer alive. Completed files and a bounded manifest restore on relaunch. Canceling or dismissing Save to Files keeps the app copy; removing it later does not delete exported copies. An interrupted transfer restores without a cross-launch retry token. If a partial file remains, it is labeled Recovered and its completion is explicitly unverified; otherwise the row directs the user back to the website. The app does not claim to resume across process termination.

Private downloads belong to a separate temporary manager and WebKit profile. Closing the last private tab cancels transfers, invalidates pending retries, removes previews/export presentation data and deletes private files. A new private session receives a new manager. Previous-process temporary download files are removed once at process startup. Only an explicit Files export retains a private file outside the session.

## Transfer and storage boundaries

- Uses public `WKDownload.progress`, `WKWebView.resumeDownload(fromResumeData:)`, and `WKWebView.startDownload(using:)`. Requests remain in WebKit; safe restarts reuse the original webpage context and resume uses WebKit’s opaque token. No URLSession re-download bypass is introduced.
- Resume tokens and original GET requests are retained only in memory. Retry prefers WebKit resume data when supplied. A GET can restart only while its original webpage context still exists unchanged; merely creating another web view with the same data store does not preserve WebKit’s cookie context. If that context is gone and no resume token is available, the row directs the user back to the website. POST/body requests are not automatically replayed. Cancel keeps partial bytes for a possible in-session WebKit resume; Remove deletes them. When neither path is available, the row asks the user to return to the website.
- Each transfer has a distinct UUID directory. Server filenames are sanitized to a leaf name, stripped of control/directional spoofing characters, and bounded by UTF-8 byte length. Restored manifests reject unsafe paths, duplicate IDs, symbolic links and oversized input. Missing files become failed rows; changed files and files absent from a damaged manifest become explicitly unverified Recovered rows. A bounded directory scan counts actual retained files, including records beyond the visible 200-item limit; removing rows reveals additional recovered files. Unexpected or unreadable directory structures block new downloads until cleaned up.
- Maximum 10 concurrent transfers, 200 retained records, 1 GiB per file and 2 GiB of download storage. Known response sizes are checked before choosing a destination; actual progress and final on-disk aggregate size are also checked. Limits stop the transfer with an explanation rather than evicting someone else's saved file.
- The manifest stores only ID, filename, date, byte size and status. It contains no source URL, request headers, cookies, page content or opaque resume data. Download files use data protection and are excluded from operating-system backup.
- Normal downloaded content is deliberately persistent app data. Users can remove individual copies in Downloads. A filesystem deletion failure keeps the row and reports that removal needs to be retried, rather than claiming success. Private content is temporary until explicitly exported. `PRIVACY.md` and the in-app privacy explanation describe this distinction.

## Verification

`Tests/DownloadStoreTests.swift` exercises path/name sanitization, UTF-8 and archive bounds, persistence, byte-size validation, duplicate IDs, symlink refusal, removal isolation, failed deletion, damaged-manifest recovery, orphan byte accounting and private no-manifest/cleanup behavior (28 assertions).

The Debug-only native `--browser-checks --download-checks` suite exercises real WebKit navigation-to-download conversion, progress, normal tab closure, retained-file restore, exporter dismissal, per-transfer cancellation, authenticated GET retry, network-failure retry, stale callbacks, private cleanup and manifest privacy using loopback-only fixtures. Its receipt is `Library/Caches/DownloadChecks.txt`; the standard native script includes it.

Build and runtime outcomes are recorded in the roadmap and review evidence after execution. Background execution under iOS suspension, physical-device touch/energy, signed-device Files providers, full spoken VoiceOver and arbitrary authenticated servers remain separate checks. Files-provider export success depends on the provider. No universally resumable/background-transfer claim is made.
